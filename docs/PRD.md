# Wellnest PRD (Product Requirements Document)

| 항목 | 내용 |
|---|---|
| 서비스명 | **Wellnest** (Wellness + Nest) |
| 한 줄 정의 | 할 일과 루틴을 관리하면서 식단·운동 기록까지 한곳에 남기는 웰니스 투두 웹앱 |
| 문서 버전 | v1.0 |
| 작성일 | 2026-08-03 |
| 플랫폼 | 웹 (모바일 퍼스트 반응형, 추후 네이티브 앱 전환 고려) |

## 1. 프로젝트 배경

건강 관리는 "특별한 이벤트"가 아니라 **매일 반복되는 작은 실천의 누적**으로 만들어진다. 그런데 현재 시장의 도구들은 이 실천을 세 갈래로 쪼개 놓았다.

- **투두 앱** (Todoist, TickTick 등) — 할 일은 잘 관리하지만 건강 데이터를 담지 못한다.
- **식단 앱** (MyFitnessPal, 다이어트신 등) — 칼로리는 기록되지만 "오늘 뭘 해야 하는지"와 연결되지 않는다.
- **운동 앱** (Strava, 삼성헬스 등) — 운동 세션만 다루고 일상 루틴과 분리되어 있다.

사용자는 결국 하루 동안 앱 세 개를 오간다. 그 결과 **기록의 마찰(friction)** 이 커지고, 2~3주 안에 대부분 중단한다. 습관 형성 연구에서 반복 실패의 주요 원인으로 지목되는 것도 "기록 비용"이다.

Wellnest는 이 세 가지를 **하나의 하루 단위 흐름**으로 합친다. 오늘 할 일을 체크하는 그 화면에서 아침 식사와 저녁 운동을 함께 남길 수 있다면, 기록은 별도의 과업이 아니라 일과의 일부가 된다.

## 2. 문제 정의

### 2.1 핵심 문제

> **"건강한 습관을 만들고 싶은 사람이, 실천(할 일)과 결과(식단·운동 기록)를 따로 관리하느라 둘 다 오래 지속하지 못한다."**

### 2.2 문제 세부 분해

| # | 문제 | 현상 | 영향 |
|---|---|---|---|
| P1 | **도구 분산** | 할 일·식단·운동을 서로 다른 앱에 기록 | 앱 전환 비용 → 기록 누락 |
| P2 | **반복 입력 피로** | 매일 같은 루틴("물 2L", "스트레칭")을 매번 새로 입력 | 3일 내 이탈 |
| P3 | **맥락 단절** | "오늘 운동하기"라는 할 일과 "오늘 30분 러닝했다"는 기록이 연결되지 않음 | 성취감 부족, 동기 저하 |
| P4 | **기록의 휘발** | 메모 앱·카카오톡 나에게 보내기로 남긴 기록은 다시 찾아보기 어려움 | 회고 불가 → 개선 없음 |
| P5 | **시각적 증거 부재** | 식단은 텍스트만으로 기억나지 않음 | 기록의 신뢰도·재미 저하 |

### 2.3 문제를 겪는 순간 (Trigger Moment)

- 아침에 일어나 "오늘 뭘 해야 하지?"를 떠올릴 때 → 루틴이 자동으로 준비되어 있지 않음
- 점심 먹고 사진은 찍었지만 어디에 남길지 애매할 때
- 일주일 뒤 "내가 지난주에 운동을 몇 번 했더라?"가 궁금할 때

## 3. 서비스 목표

### 3.1 사용자 목표 (User Goal)

- **10초 안에** 오늘의 할 일 확인과 기록 입력을 끝낸다.
- 매일 반복되는 루틴을 **한 번만 등록**하고, 이후에는 체크만 한다.
- 실천과 기록이 **한 화면**에 모여 하루의 성취를 즉시 확인한다.

### 3.2 제품 목표 (Product Goal)

| 목표 | 지표 (North Star / 보조) |
|---|---|
| 기록 마찰 최소화 | 기록 1건 입력까지 **탭 3회 이내**, 소요 **15초 이내** |
| 습관 지속 | 가입 후 **7일 연속 기록률 40%** 이상 |
| 통합 사용 | 주간 활성 사용자 중 **투두 + 기록 둘 다 사용 비율 60%** 이상 |
| 데이터 신뢰 | 기록 유실 0건 (서버 저장, 새로고침·기기 변경에도 유지) |

### 3.3 비목표 (Non-Goal)

- 정밀한 영양소 분석 / 음식 DB 연동 (칼로리는 사용자 직접 입력)
- 웨어러블·헬스킷 연동을 통한 자동 수집
- 소셜 피드, 친구 팔로우, 랭킹
- 전문가 코칭·PT 매칭

## 4. 대상 사용자

### 4.1 1차 타깃 (Primary)

**"습관을 만들고 싶은 20~30대 직장인·학생"**

- 건강 관리에 관심은 높지만 시간이 부족하다.
- 이미 투두 앱을 써봤지만 건강 항목까지는 관리하지 못했다.
- 스마트폰으로 하루 대부분의 기록을 남긴다. → **모바일 퍼스트가 필수**

### 4.2 퍼소나

#### 퍼소나 A — 김수민 (28세, 마케터)

| 항목 | 내용 |
|---|---|
| 상황 | 야근이 잦아 식사가 불규칙, 운동은 주 1회 겨우 |
| 목표 | "일단 아침에 물 마시기·스트레칭부터 꾸준히" |
| 페인포인트 | 투두 앱에 건강 항목을 넣어도 "체크만 하고 끝" → 실제 뭘 먹고 뭘 했는지 남지 않음 |
| 기대 | 체크하는 김에 사진 한 장으로 오늘의 식단이 남았으면 |

#### 퍼소나 B — 박준호 (34세, 개발자)

| 항목 | 내용 |
|---|---|
| 상황 | 헬스장을 3개월 등록했지만 기록은 앱마다 흩어짐 |
| 목표 | 주 3회 운동 루틴 유지, 한 달 뒤 돌아보기 |
| 페인포인트 | "지난주에 몇 번 갔지?"를 확인할 방법이 없음 |
| 기대 | 루틴을 한 번 만들어두면 매일 자동으로 오늘 할 일에 뜨는 것 |

### 4.3 2차 타깃 (Secondary)

- 다이어트·체중 관리 중인 사용자
- 재활·컨디션 회복 중이라 매일의 상태를 남겨야 하는 사용자

## 5. 핵심 기능

| # | 기능 | 설명 | 스펙 문서 |
|---|---|---|---|
| F1 | **구글 로그인** | Supabase Auth 기반 Google OAuth. 첫 로그인 시 프로필 자동 생성 | [01-auth-google-login.md](./specs/01-auth-google-login.md) |
| F2 | **오늘 화면** | 오늘의 할 일 + 루틴 체크 + 오늘 기록 요약을 한 화면에 | [02-today-dashboard.md](./specs/02-today-dashboard.md) |
| F3 | **투두 CRUD** | 할 일 등록·조회·수정·삭제, 완료 체크 | [03-todo-crud.md](./specs/03-todo-crud.md) |
| F4 | **루틴 CRUD** | 반복 요일을 지정한 루틴 등록·조회·수정·삭제. 해당 요일에 오늘 할 일로 자동 노출 | [04-routine-crud.md](./specs/04-routine-crud.md) |
| F5 | **웰니스 기록 CRUD** | 식단·운동을 하나의 기록으로 통합 관리. 사진 첨부 | [05-wellness-log-crud.md](./specs/05-wellness-log-crud.md) |
| F6 | **이미지 업로드** | Supabase Storage에 기록 사진·프로필 사진 업로드 및 노출 | [06-image-upload.md](./specs/06-image-upload.md) |
| F7 | **프로필** | 닉네임 수정, 아바타 업로드, 로그아웃 | [07-profile.md](./specs/07-profile.md) |

### 5.1 정보 구조 (IA)

```
Wellnest
├── /login                 비로그인 진입점 — 구글 로그인
├── /            (탭 1)    오늘 — 루틴 체크 + 오늘 할 일 + 오늘 기록 요약
├── /routines    (탭 2)    루틴 — 목록 / 생성 / 수정 / 삭제
├── /logs        (탭 3)    기록 — 식단·운동 목록 / 생성 / 수정 / 삭제
└── /profile     (탭 4)    프로필 — 아바타·닉네임 / 통계 / 로그아웃
```

### 5.2 데이터 모델

```
auth.users (Supabase 관리)
   │
   ├─1:1─ profiles   (id, email, display_name, avatar_url)
   │
   ├─1:N─ routines   (title, emoji, category, repeat_days[], is_active, sort_order)
   │         │
   │         └─1:N─ todos (routine_id 로 연결 — 루틴에서 파생된 오늘의 할 일)
   │
   ├─1:N─ todos      (title, memo, due_date, priority, is_done, completed_at)
   │
   └─1:N─ logs       (log_type: meal|workout, logged_on, title, memo, image_url,
                      meal_type, calories, duration_min)
```

> **설계 의도** — 식단과 운동을 별도 테이블로 나누지 않고 `logs` 하나에 `log_type`으로 구분했다.
> 두 기록은 "언제 / 무엇을 / 사진 / 메모"라는 공통 골격이 동일하고, 타입별 필드만 다르다.
> 통합함으로써 (1) 오늘 화면에서 하나의 타임라인으로 보여줄 수 있고,
> (2) 추후 '수면', '수분 섭취' 같은 기록 타입을 테이블 추가 없이 확장할 수 있다.
> 타입별 필드 정합성은 DB `CHECK` 제약으로 보장한다.

## 6. 사용자 시나리오

### 시나리오 1 — 첫 진입 및 루틴 설정 (신규 사용자)

> 수민은 인스타 광고를 보고 Wellnest에 접속했다.

1. `/` 접속 → 비로그인 상태이므로 `/login`으로 자동 이동
2. **"Google로 시작하기"** 버튼 탭 → 구글 계정 선택
3. 로그인 완료 → 프로필이 자동 생성되고 `/`(오늘)로 이동
4. 오늘 화면이 비어 있고 **"첫 루틴을 만들어보세요"** 안내가 보임
5. 하단 탭에서 **루틴** → `+` 버튼 → "아침 스트레칭" 입력, 이모지 🧘, 반복 요일 **월·화·수·목·금** 선택 → 저장
6. **오늘** 탭으로 돌아오니 오늘이 화요일이므로 "아침 스트레칭"이 오늘의 루틴에 노출됨

**성공 기준**: 가입부터 첫 루틴 등록까지 **2분 이내**

---

### 시나리오 2 — 하루 사용 흐름 (일상 사용자)

> 준호의 화요일.

| 시각 | 행동 | 화면 |
|---|---|---|
| 07:30 | 앱 열기 → "아침 스트레칭" 체크 | `/` 오늘 |
| 08:10 | 아침 식사 사진 촬영 → **기록 추가** → 식단 / 아침 / "오트밀과 바나나" / 사진 첨부 / 320kcal → 저장 | `/logs` |
| 12:40 | 점심 기록 추가 (사진 없이 텍스트만) | `/logs` |
| 19:00 | "퇴근 후 헬스" 할 일 추가 → 우선순위 높음 | `/` 오늘 |
| 21:30 | 운동 기록 추가 → 운동 / "하체 + 러닝" / 55분 → 저장 → "퇴근 후 헬스" 체크 | `/logs`, `/` |
| 23:00 | 오늘 화면에서 **루틴 1/1, 할 일 2/2, 기록 3건** 확인 | `/` |

**성공 기준**: 기록 1건 입력이 **탭 3회 · 15초 이내**

---

### 시나리오 3 — 기록 수정 (오입력 정정)

> 수민은 어제 저녁 칼로리를 잘못 입력했다.

1. **기록** 탭 → 날짜 필터에서 어제 선택
2. "저녁 - 김치찌개" 카드 탭 → 상세/수정 화면 열림
3. 칼로리 `800` → `650`으로 수정, 사진도 교체 → **저장**
4. 목록으로 돌아오면 즉시 반영된 값이 보임
5. 브라우저를 새로고침해도 수정값이 유지됨 (서버 저장)

**성공 기준**: 수정 결과가 조회 화면과 새로고침 후에 모두 반영

---

### 시나리오 4 — 정리 (삭제)

> 준호는 더 이상 하지 않는 루틴을 정리한다.

1. **루틴** 탭 → "저녁 조깅" 카드의 `⋯` → **삭제**
2. 확인 모달 — *"삭제하면 되돌릴 수 없어요. 이미 만들어진 할 일은 남습니다."*
3. **삭제** 확정 → 목록에서 사라짐
4. 새로고침해도 다시 나타나지 않음

**성공 기준**: 삭제된 데이터는 어떤 화면에서도 조회되지 않음

---

### 시나리오 5 — 프로필 사진 등록

1. **프로필** 탭 → 아바타 영역 탭
2. 이미지 선택 → 업로드 진행 표시
3. 업로드 완료 후 프로필 화면과 오늘 화면 헤더에 즉시 반영
4. 다른 기기에서 로그인해도 동일한 사진이 보임

**성공 기준**: 업로드한 이미지가 서비스 화면에서 확인 가능

## 7. MVP 범위

### 7.1 포함 (In Scope) — v1.0

| 영역 | 포함 내용 |
|---|---|
| **인증** | 구글 로그인 / 로그아웃 · 세션 유지 · 비로그인 접근 차단 |
| **투두** | 생성 · 조회(날짜별) · 수정 · 삭제 · 완료 체크 · 우선순위 |
| **루틴** | 생성 · 조회 · 수정 · 삭제 · 반복 요일 지정 · 활성/비활성 · 오늘 화면 자동 노출 |
| **기록** | 식단/운동 통합 생성 · 조회(날짜별) · 수정 · 삭제 · 타입별 필드(식사종류·칼로리 / 운동시간) |
| **이미지** | 기록 사진 업로드·교체·삭제, 프로필 아바타 업로드 (Supabase Storage) |
| **프로필** | 닉네임 수정 · 아바타 · 간단 통계(오늘 달성률) · 로그아웃 |
| **UI/UX** | 모바일 퍼스트 반응형(375px 기준 → 태블릿/데스크톱 대응), 하단 탭 내비게이션, 로딩·빈 상태·에러 상태 |
| **디자인 시스템** | 컬러 파운데이션 · 타이포그래피 · 공통 UI 컴포넌트 · 화면 UI (.pen) |
| **인프라** | Supabase(Auth/Postgres/Storage) + RLS, Vercel 배포 |

### 7.2 제외 (Out of Scope) — v1.0에서 하지 않는 것

| 제외 기능 | 제외 사유 | 재검토 시점 |
|---|---|---|
| 이메일/비밀번호 · 카카오 · 애플 로그인 | 구글 하나로 MVP 검증 충분, 인증 UX 복잡도 증가 | v1.1 |
| 음식 DB 연동 자동 칼로리 계산 | 외부 API 의존·비용 발생, 직접 입력으로 대체 가능 | v2.0 |
| 웨어러블/헬스킷 자동 수집 | 네이티브 앱 전환 이후에나 가능 | 앱 전환 시 |
| 주간·월간 통계 대시보드, 차트 | 데이터가 쌓여야 의미 있음. MVP는 "쌓는 것"에 집중 | v1.1 |

### 7.3 릴리스 기준 (Definition of Done)

v1.0은 다음을 **모두** 만족할 때 완료로 본다.

- [ ] 배포된 공개 URL에서 구글 로그인이 정상 동작한다.
- [ ] 투두·루틴·기록 각각에 대해 생성/조회/수정/삭제가 동작하고, **새로고침 후에도 유지**된다.
- [ ] 모든 데이터가 Supabase Postgres에 저장된다 (로컬/세션 스토리지 사용 금지).
- [ ] 이미지 1개 이상을 업로드할 수 있고, 서비스 화면에서 보인다.
- [ ] 다른 사용자의 데이터에 접근할 수 없다 (RLS 검증).
- [ ] 375px 모바일 화면에서 가로 스크롤 없이 모든 화면이 사용 가능하다.
- [ ] 5개 화면 모두 디자인 시스템(.pen)과 일관된 UI로 구현되어 있다.

## 8. 추후 앱 전환 고려사항

이번 v1.0은 웹이지만, 다음 원칙으로 **React Native 전환 비용을 미리 낮춰** 둔다.

| 원칙 | 적용 |
|---|---|
| **모바일 퍼스트 레이아웃** | 375px 기준 설계 · 하단 탭 내비게이션 · 터치 타깃 최소 44px |
| **로직/뷰 분리** | 데이터 접근·비즈니스 로직은 `src/lib`, `src/features/*/actions.ts`에 격리 → RN에서 그대로 재사용 |
| **디자인 토큰화** | 컬러·타이포를 CSS 변수 + 토큰 이름으로 관리 → RN StyleSheet로 1:1 이식 가능 |
| **플랫폼 중립 컴포넌트 명명** | `BottomSheet`, `AppBar`, `TabBar` 등 네이티브 대응물이 존재하는 이름 사용 |
| **Supabase 유지** | `@supabase/supabase-js`는 RN에서도 동일 API로 동작 → 백엔드 재작성 불필요 |
| **웹 전용 API 회피** | `localStorage`, `window` 직접 의존 최소화 |
