# SPEC-05 · 웰니스 기록 (식단 · 운동) CRUD

| 항목 | 내용 |
|---|---|
| **기능명** | 식단 / 운동 기록 등록 · 조회 · 수정 · 삭제 |
| 관련 화면 | `/logs`, `/logs/new`, `/logs/[id]/edit`, `/` (오늘 요약) |
| 관련 테이블 | `logs` (+ Supabase Storage `log-images`) |
| 우선순위 | P0 (필수) |

---

## 1. 기능 목적

- 오늘 무엇을 먹고 어떤 운동을 했는지 **사진 한 장과 함께** 남기게 한다.
- 식단과 운동을 **하나의 타임라인**으로 관리해 앱 전환 없이 하루를 기록하게 한다.
- 나중에 날짜별로 돌아보며 스스로의 패턴을 확인하게 한다.

---

## 2. 데이터 정의

`logs` 테이블 하나로 두 타입을 처리하고, `log_type`으로 구분한다.

| 컬럼 | 타입 | 필수 | 적용 타입 | 제약 / 기본값 |
|---|---|---|---|---|
| `id` | uuid | ✅ | 공통 | `gen_random_uuid()` |
| `user_id` | uuid | ✅ | 공통 | 세션에서 주입 |
| `log_type` | text | ✅ | 공통 | `meal` \| `workout` |
| `logged_on` | date | ✅ | 공통 | 기본 오늘 (Asia/Seoul) |
| `title` | text | ✅ | 공통 | 1~120자 |
| `memo` | text | ✖ | 공통 | 최대 500자 |
| `image_url` | text | ✖ | 공통 | Storage 공개 URL (SPEC-06) |
| `meal_type` | text | ✖ | **meal** | `breakfast` \| `lunch` \| `dinner` \| `snack` |
| `calories` | integer | ✖ | **meal** | 0 이상 |
| `duration_min` | integer | ✖ | **workout** | 0 이상 |

### 2.1 타입별 필드 정합성

DB `CHECK` 제약으로 강제한다.

```sql
constraint logs_type_fields_chk check (
  (log_type = 'meal'    and duration_min is null)
  or
  (log_type = 'workout' and meal_type is null and calories is null)
)
```

→ 운동 기록에 칼로리가 들어가거나, 식단 기록에 운동 시간이 들어가는 **데이터 오염을 DB 레벨에서 차단**한다.

---

## 3. 동작 방식

### 3.1 생성 (Create)

1. `/logs` FAB `+` 또는 오늘 화면 **기록 `+ 추가`**
2. 최상단 **SegmentedControl** 로 타입 선택 — `🍽 식단` / `🏃 운동`
3. 타입에 따라 입력 폼이 전환된다.

| 공통 | 식단 전용 | 운동 전용 |
|---|---|---|
| 날짜 (기본 오늘) | 식사 종류 (아침/점심/저녁/간식) | 운동 시간 (분) |
| 제목 (필수) | 칼로리 (kcal, 선택) | |
| 메모 (선택) | | |
| 사진 (선택) | | |

4. **저장** → 사진이 있으면 먼저 Storage 업로드(SPEC-06) → 반환된 URL을 `image_url`로 저장
5. 성공 → `/logs`로 이동 + 토스트 *"기록을 남겼어요"*

> 타입을 전환하면 **해당 타입에 없는 필드는 `null`로 초기화**해 CHECK 제약 위반을 예방한다.

### 3.2 조회 (Read)

| 위치 | 조회 조건 |
|---|---|
| `/logs` | 본인 기록 전체. `logged_on` 내림차순 → `created_at` 오름차순 |
| `/` (오늘) | `logged_on = 오늘` |

- `/logs`는 **날짜별 그룹 헤더**(오늘 / 어제 / 8월 1일 …)로 묶어 표시한다.
- 필터 칩: `전체` / `식단` / `운동`
- 카드 구성: 타입 아이콘 · 제목 · 부가정보(식사종류·칼로리 또는 운동시간) · 썸네일(있을 때)

### 3.3 수정 (Update)

1. 기록 카드 탭 → `/logs/[id]/edit` (기존 값 프리필)
2. 모든 필드 수정 가능 — **타입 변경도 허용**
3. 사진은 **교체 / 삭제 / 유지** 세 가지 선택
   - 교체: 새 파일 업로드 후 `image_url` 갱신, 이전 파일은 Storage에서 제거
   - 삭제: `image_url = null` + Storage 파일 제거
4. **저장** → `updateLog(id, patch)` → `/logs`로 복귀, 목록과 오늘 화면 모두에 반영

### 3.4 삭제 (Delete)

1. 수정 화면 하단 **삭제** 또는 카드 `⋯` → **삭제**
2. 확인 모달 — *"이 기록을 삭제할까요? 사진도 함께 삭제되며 되돌릴 수 없어요."*
3. 확정 → `image_url`이 있으면 Storage 파일 삭제 → `logs` 행 삭제
4. 목록에서 제거 + 토스트 *"삭제했어요"*

## 4. 예외 처리

| # | 상황 | 처리 |
|---|---|---|
| E1 | 제목 미입력 / 공백만 | 저장 비활성화 + 인라인 에러 *"무엇을 기록할지 입력해 주세요"* |
| E2 | 칼로리 / 운동 시간에 **음수 또는 문자** 입력 | 숫자 전용 입력 + 0 미만 차단, 인라인 에러 *"0 이상의 숫자를 입력해 주세요"* |
| E3 | 칼로리 비현실적 값 (예: 100,000) | 상한 10,000kcal / 운동 1,440분 제한 + 안내 |
| E4 | 타입 전환 후 이전 타입 필드가 남아 CHECK 위반 | 전환 시 해당 필드를 `null`로 초기화 (클라이언트 + 서버 양쪽에서 정규화) |
| E5 | 사진 업로드는 성공했는데 DB 저장 실패 | 업로드된 Storage 파일을 **롤백 삭제**해 고아 파일 방지 |
| E6 | DB 저장은 성공했는데 이전 사진 삭제 실패 | DB 저장을 우선 확정, 삭제 실패는 콘솔 경고만 (사용자 흐름 차단하지 않음) |
| E7 | 미래 날짜 선택 | 오늘 이후 날짜는 선택 불가 (달력에서 비활성) |
| E8 | 네트워크 오류로 저장 실패 | 입력값·선택한 사진 보존 + 토스트 *"저장에 실패했어요. 다시 시도해 주세요."* |
| E9 | 이미 삭제된 기록 수정 시도 | *"이미 삭제된 기록이에요"* 안내 후 `/logs`로 이동 |
| E10 | 다른 사용자의 기록 접근 | RLS 차단 → 404 처리 |
| E11 | 저장 버튼 연타 | 요청 중 `disabled` + 스피너 |
| E12 | 기록이 하나도 없음 | 빈 상태 — *"첫 기록을 남겨보세요"* + **기록 추가** CTA |

## 5. 완료 조건

- [ ] 식단 기록을 생성하면 `/logs`와 오늘 화면에 즉시 나타나고 새로고침 후에도 유지된다.
- [ ] 운동 기록을 생성하면 동일하게 동작한다.
- [ ] 식단에는 식사종류·칼로리, 운동에는 운동시간만 입력·표시된다.
- [ ] 기록의 모든 필드(타입 포함)를 수정할 수 있고, 결과가 조회 화면에 반영된다.
- [ ] 사진을 첨부·교체·삭제할 수 있고 화면에서 확인된다.
- [ ] 삭제한 기록은 목록·오늘 화면·DB 어디에서도 조회되지 않는다.
- [ ] 필터 칩(전체/식단/운동)이 정상 동작한다.
- [ ] 잘못된 타입 조합(운동 + 칼로리 등)이 저장되지 않는다.
- [ ] 모든 데이터가 Supabase `logs` 테이블에 저장된다.
